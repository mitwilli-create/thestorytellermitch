01 · THE MODULE

A safe agent-assisted change, end to end

The underlying task is real: add a manually triggered microsite generator to a production job-search system without exposing personal application data. The teaching goal is not a perfect prompt. It is a repeatable verification loop.

1. Define the observable result

Write the acceptance criteria before opening Agent: one role slug in, one hand-editable page out; four selection conditions must pass; noindex and the affiliation disclaimer must be structural; dry run must write nothing.

2. Give Agent the boundaries

Ask Agent to inspect the repository rules, existing page patterns, data contract, and test conventions. Name the files it may touch. Keep the personal apply pack out of the committed fixture.

3. Review, run, recover

Use Review Diffs before accepting the change. Run the focused test in Cursor's terminal. If the change is wrong, restore the Agent checkpoint for the edit, but use Git for permanent history. Cursor documents those as separate recovery layers.

02 · THE VERIFICATION LOOP

A lesson is complete when the learner can prove the change

Choosing the task and letting Agent work are the setup. The lesson is the proof: the learner inspects the change, proves it, and knows how to recover.

Red: make the missing behavior visible

The first integration run fails because the generator does not exist. That failure proves the test can catch the missing behavior instead of merely describing source code.

Green: implement only the promised behavior

The generator reads a role-level JSON brief, validates the selection gate, escapes outward copy, confines output to the site root, and writes atomically. Nine focused integration tests cover the user-visible contract.

Recovery is part of fluency

Checkpoints undo Agent edits; Git preserves permanent history. Teaching the distinction prevents the most common failure in AI-assisted coding: moving fast without knowing what state can be recovered.

03 · THE FUNCTION

The first 90 days: from audit to a release-coupled function

The sequence starts with evidence, turns that evidence into a roadmap, and leaves behind a system an education engineering team can operate.

Days 1–30: find the adoption blockers

Start with the places developers get stuck: support categories and failed tasks. Use product telemetry, community questions, and the current learning library to rank each gap by support volume, release timing, and enterprise rollout risk. The output is a short owned backlog, not an audit that sits on a shelf.

Days 31–60: ship the zero-day loop

Pair one upcoming model or agent release with a workflow-based learning path, acceptance test, recovery step, and support-deflection hypothesis. Education joins release planning early enough that the verified tutorial ships with the capability.

Days 61–90: make the function repeatable

Publish the editorial rules and release intake, then give the team a backlog rubric and feedback cadence. The first hiring scorecard follows the same logic. Measure task success and time to first verified outcome against the named support category each lesson is expected to shrink.
